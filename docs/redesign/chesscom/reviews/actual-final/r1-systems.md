# Независимое post-implementation review — UI Systems Architect

**CHANGES REQUIRED.** Постраничная архитектура стала заметно яснее, интеграция `/home` выполнена, но устойчивость состояний Home и фактический guest/zero-state Progress не соответствуют принятой спецификации. ## Сильные стороны

1. **Маршруты наконец имеют разные силуэты.** Home предлагает понятный быстрый старт и настоящую задачу без большой стартовой доски. Play сохраняет референсную desktop-композицию доска/режимы, а mobile начинает с действия. FAQ — читаемый справочник, History — архив, Login — самостоятельная форма.
2. **Focused Game освобождает доску и сохраняет доступ к системе.** На desktop нет постоянного sidebar, на mobile доска имеет полезный размер. Кнопка меню действительно связана с существующим `main-sidebar`; drawer использует общий Overlay, inert, Escape и возврат фокуса. Навигация/язык/account не переписаны второй независимой системой. Уход в лобби — обычная ссылка, а не скрытая сдача партии.
3. **Spring/Thymeleaf-контракт `/home` реализован предметно.** PageController содержит alias, SecurityConfig публично разрешает его; SeoService назначает home metadata, canonical и hreflang к `/`, не добавляя alias в индексируемые пути. Разделение `/play` по `id`/`code` сохранено; общий JS учитывает `/home` при сохранении языка.
4. **Мобильный архив полезен без горизонтального угадывания.** Populated History показывает дату, режим, игроков, исход и явное действие открытия. Guest History честно объясняет ограничения. Общая локальная типографика, двухдисковая марка и настоящие шашечные фигуры удерживают страницы в одной системе.

## Критические проблемы и исправления

### P1 — Временный сбой `/api/auth/me` уничтожает локальную сессию Home/Play

В `lobby.js`, `refreshMe()`, любой exception вызывает `Checkers.Auth.clear()`. Это включает сетевую недоступность и серверную ошибку, а не только подтверждённую невалидность авторизации. Затем `refreshUI()` показывает гостевое состояние и скрывает персональное продолжение/историю. Следующий быстрый старт может через `ensureAuth()` создать новую guest-сессию. Это опасная подмена состояния аккаунта при обычном отказе сети; спецификация требует независимо восстанавливаемых ошибок.

**Исправить:** очищать credentials только по подтверждённому auth rejection с учётом существующего refresh flow. При network/5xx сохранять сессию, показывать локализованную ошибку проверки аккаунта и Retry, не подменять аккаунт гостем и не представлять сохранённую статистику как только что подтверждённую. Не блокировать общие публичные переходы. Проверить зарегистрированную сессию при offline/500 `/me`, затем восстановление и онлайн-старт: token/account должны сохраниться.

### P2 — Home не владеет loading/error состояниями каждого модуля полностью

`loadActiveGames()` не показывает loading, а секция изначально hidden: pending выглядит как отсутствие активной игры. `loadRecentGames()` открывает секцию до ответа API, но начальный `recentEmpty` уже видим: во время ожидания можно получить ложное «Нет партий». В catch active/recent старые строки не очищаются и не помечаются stale; после повторного сбоя они соседствуют с ошибкой как будто актуальны. Для daily preview ошибка записывается внутрь `[data-task-preview]`, который в шаблоне имеет `aria-hidden="true"`; описание ошибки и его `aria-label` остаются скрыты для accessibility tree. Retry есть, но не заменяет доступного объяснения ошибки. Preview также не имеет явного loading сообщения.

**Исправить:** сделать явный render-state для каждого модуля: pending/data/confirmed-empty/error. Recent empty показывать только после успешного пустого ответа; active pending озвучивать в стабильном status. Старые данные либо скрывать при ошибке, либо явно помечать как последние успешно полученные. Daily status вынести в отдельный видимый и доступный `role=status` вне декоративной мини-доски; сохранять ссылку на Tasks и Retry. Проверить задержанный ответ, первичный отказ, повторный отказ после успеха и успешный retry отдельно для трёх модулей.

### P2 — Progress всё ещё использует метрику-заглушку как гостевой экран и показывает ложные начальные значения

`progress-1440x1000.png` показывает крупный прочерк под «Процент побед» — именно тот guest-pattern, который план запрещает. `rating.js` намеренно присваивает `'—'` гостю и аккаунту с неопределённым win-rate. В `rating.html` приватные W/L/D нули и весь content не скрыты изначально, поэтому до завершения проверки сессии/`me` они могут показываться как реальные. В populated состоянии отсутствует обязательный total; guest не имеет предусмотренного действия регистрации. Это системная проблема разделения guest/loading/zero/data, не только декоративный недостаток.

**Исправить:** отрисовывать до ответа только loading. Guest — bounded объяснение и Login/Register/Play без процентной метрики. Registered zero — подтверждённые total/W/L/D нули, понятное пояснение и Play без win-rate-плейсхолдера. Populated — total/W/L/D плюс определённый win-rate. Error/Retry — отдельное состояние. Проверить визуально guest, zero account, задержанный `/me`, populated и отказ; ни pending, ни guest не должны показывать синтетические значения.

### P2 — Продолжение активной партии не имеет заявленного приоритета и правильного mobile порядка

В `index.html` `.home-start` находится перед active-games section. Recent находится внутри main column, а daily — в следующей side column. Следовательно, при возвращении активная партия появляется после старта новой, а на mobile вся история идёт до дневной задачи. Это расходится с согласованным порядком: active → start → daily → персональные результаты. В исходниках нет перестройки DOM для состояний, которая обеспечивала бы этот контракт. Успешный registered скриншот без активной партии этого не проверяет.

**Исправить:** вынести active state до quick-start, затем расположить общий DOM так, чтобы daily шла до результатов на узкой ширине. Desktop разместить эти же области grid areas без расхождения зрительного и клавиатурного порядка. Снять populated returning Home с настоящей активной партией при 1440 и 390px; проверить Tab и чтение заголовков. Не маскировать структурную проблему одним CSS `order`.

## Другие отклонения и конкретные улучшения

- **CSS снова развивается слоями overrides.** В `app.css` сохранены старые game/dashboard/mobile определения и добавлены повторные `.mobile-top/.bottom-nav`, game shell и responsive блоки после них; у ghost borders также есть поздний override. В частности, preview скрывается при `max-width:1199px`, хотя утверждённая граница — `<1180px`. Это не доказывает сломанный экран на 1190px, но показывает, что принятый контракт токенов/правил не стал единственным источником. Свести правила одного компонента/брейкпоинта в одно место и убрать устаревшие game1200-комментарии, поскольку drawer теперь включён во всех game widths. Оставить foundations в `design-system.css`, page compositions в `app.css`, явную согласованную границу preview.
- **Правила русских шашек недостаточно обозначены перед стартом.** Home heading остаётся общим «Ваше игровое пространство», Play — «Играть в шашки»; обещанные «Русские шашки · 8×8» и ранняя ссылка правил не показаны. Двухдисковая марка корректна, но не сообщает вариант правил. Добавить короткий локализованный ruleset/Rules link в Home/Play/Game header контекст, сохранив компактность.
- **Tasks отклоняется от размерного и accessible-description контракта.** Desktop screenshot показывает доску около670px вместо согласованных max560px; она доходит почти до низа исходного1000px viewport. В шаблоне `aria-describedby` ссылается только на клавиатурную инструкцию, не на objective. Ограничить puzzle board согласно плану или явно обосновать новый размер; дать objective стабильный id и включить его в описание board. Short landscape/zoom и feedback states по этим снимкам не сертифицированы.
- **Home metrics не соответствуют согласованному набору W/L/D.** Сейчас это games/wins/win-rate; losses/draws отсутствуют. При zero total выводится прочерк rate. Привести Home summary к total/W/L/D и скрывать неопределённый rate; никаких нулей до подтверждённых данных.
- **Семантика mobile history требует настоящей AT проверки.** Визуальное преобразование table/tbody в block и tr в grid выглядит хорошо, но само по себе не удостоверяет сохранение таблицы в accessibility tree каждого браузера. Провести проверку с screen reader, не считая CSS-generated data-label гарантией корректного чтения.
